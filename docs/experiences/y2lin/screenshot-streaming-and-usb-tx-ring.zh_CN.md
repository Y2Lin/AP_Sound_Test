# FAP\_SCREENSHOT\_V1 第二次落地：流式采集与 USB TX 环

把 **AP\_CyberClock**（赛博朋克时钟，另一个 AI Passport 应用）发布到社区市场时第二次实现了
`FAP_SCREENSHOT_V1` 协议，对应固件 v10.4 → v10.4.2（提交 `59a821e` 至 `855138f`）。
第一条经验（[serial-screenshot-protocol](serial-screenshot-protocol.zh_CN.md)）走的是快照路线：
整屏一次性渲染进静态预留缓冲再发出。本条记录另一条路线——拦截显示刷新回调、
逐条带流式采出——以及第一次没踩到的 USB 驱动发送环形缓冲与 Web Serial 主机侧的坑。
两条路线在无 PSRAM 的 ESP32-C3 上都成立，选型依据在文末。

## 驱动安装时就把 TX 环扩到 4KB

`usb_serial_jtag` 驱动的发送侧是一个 FreeRTOS 环形缓冲，默认 `tx_buffer_size` 只有
256 字节，而 `xRingbufferSend()` 要求条目连续放入：任何大于环容量的单次写入立即失败
（"data will never ever fit"），一个字节都进不去。v10.4.2 之前设备每单必回
`ERR SHOT`，主机侧报"像素数据在声明长度之前结束，10/153600"——那 10 个字节其实
是设备回的 `ERR SHOT\r\n` 文本，不是像素。修复是两件事一起做：驱动安装时显式
`tx_buffer_size = 4096`，像素分片改为 1KB 一段发送。教训有二：分片尺寸要对着
TX 环容量规划，而不是对着载荷本身；主机报"数据不足"时，先怀疑设备其实回了
一行错误文本。

## 无 PSRAM 真机上，150KB 整帧分配必然失败

v10.4 最初沿用快照思路，在系统堆一次性 `malloc(153600)`（240×320×2）。这套代码
在堆富余时没问题，但真机上 LVGL、NimBLE 与各任务跑起来之后，最大连续空闲块
给不出 150KB，于是每一单截屏都 `ERR SHOT`。v10.4.1 改成流式：临时包装显示刷新
回调，把每个 20 行条带拷进 3 格环形槽（每格 240×24×2 = 11.5KB，共 34.5KB，
峰值内存约为旧方案的 1/4.4），USB 任务边收边发；环满时生产者小睡背压，
双侧共享中止标志保证失败路径干净收尾。在无 PSRAM 的芯片上，任何接近整屏
尺寸的连续缓冲都不要指望运行时堆。

## LVGL 9.2 没有公开的刷新回调 getter

流式采集要临时替换 `flush_cb`，而 LVGL 9.2 没有公开的 `lv_display_get_flush_cb()`
（9.5 才补上）。只能引入 `display/lv_display_private.h` 直读 `disp->flush_cb`。
直读私有字段之外，真正的风险是不对称挂钩：如果卸载时把包装函数误存成"原回调"，
下一次包装就会无限递归。防线是给钩子建生命周期状态机（空闲 / 等挂钩 / 活跃 /
发送中 / 中止），卸载只发生在"确信已挂钩"的路径上，活跃态不动回调，发送结束
与超时路径都有兜底卸钩双保险。

## VFS 控制台把 \n 翻译成 \r\n——二进制窗口内全局静默日志

日志走 VFS 控制台路径时，每个 `\n` 都被翻译成 `\r\n`，任何一个日志字节混进像素流
都会让图像从该字节起整体错位。协议头行第一个字节发出之前
`esp_log_level_set("*", ESP_LOG_NONE)`，最后一个像素字节之后恢复默认级别。
与第一篇相同的结论，这次再补一条：静默与恢复必须覆盖所有退出路径（成功、
超时、中止、USB 断开），否则一次失败留下的全局静默会把后续诊断变成盲飞。

## 失败要机器可读：ERR SHOT 加原因码

v10.4.2 给 `ERR SHOT` 回复追加了原因码：`BUSY`（上一单未结束）、`MEM`（环形缓冲
分配失败）、`HOOK`（3 秒内未完成挂钩）、`DATA`（挂钩后 3 秒无首块）、`STALL`
（流式中 3 秒无新块）、`USB`（USB 写入失败）、`SHORT`（发送量不足）。v10.4 →
v10.4.1 修 `MEM`、v10.4.1 → v10.4.2 修 `USB`，两次真机定位都是原因码一眼看穿，
网页截屏页也据此展示原因而不是盲目重试。调试型协议从第一版起就定义机器可读
的失败语义，比事后补日志便宜得多。

## Web Serial 主机侧的四条纪律

- **DTR/RTS 保持常低**：否则关闭串口时的电平边沿会触发 ESP32-C3 内置下载复位通路，
  设备当场重启（本应用的 v9.1 已付过一次学费，截屏会话同样适用）。

- **单读者泵循环**：串口读循环独占、顺序消费，不要并发竞争读。

- **每次读取都带超时**：`read()` 无限等待会把整个页面卡死。

- **设备错误行上抛显示**：非像素字节不要静默丢弃——它往往就是 `ERR SHOT <原因>`，
  是定位问题的关键证据。

## 发布流程侧记（publisher 事实）

- 截屏回执 **24 小时有效**：发布提交用的连接证明要在现场重拍，隔天的旧回执不作数。

- **已有版本在审时新版本会被拒**（提示"已有版本正在审核"）：发布节奏必须串行，
  等审核完成再提下一版。

## 对下一个应用的泛化

- 串口载荷分片尺寸 = min(应用需求, TX 环容量 − 余量)；TX 环在驱动安装时显式配置，
  不吃默认值。

- 无 PSRAM 芯片上，超过整屏 1/8 的连续缓冲预算改成分带流式 + 有界环形槽。

- 拦截刷新回调前先确认 LVGL 版本有无公开 getter；直读私有头文件时必须配对称
  卸载与防递归状态机。

- 二进制协议与文本日志在时间上互斥，静默/恢复要覆盖全部退出路径。

- 快照路线 vs 流式路线：需要"任意时刻整屏一致帧"且能静态预留整屏缓冲时选快照；
  堆紧张、想边渲染边发送、或要顺手做截屏压缩时选流式。
